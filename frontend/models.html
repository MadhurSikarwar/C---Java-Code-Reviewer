Notes on the method

How a verdict is reached.

IntelliReview doesn’t hand your file to one model and print whatever comes back. It reads the code, collects findings, and only then asks a model how they add up. Here is each step, and how well the whole thing works when it is tested honestly.

1

It parses the file.

C goes through a real C parser, Java through a real Java parser. Real code refers to types declared in headers we can’t see (pthread_t, HANDLE, your own typedefs), so when the parser stumbles on an unknown type name it learns it and tries again, rather than giving up.

C++ can’t be parsed that way, so it gets a lighter, pattern-based read.

You will knowEvery review says whether it was a full parse or a heuristic one, in the measurements list.
2

It follows the data.

For each C function it builds a control-flow graph and follows every pointer through it: allocated, checked for NULL, freed, moved, handed to another function. It knows that if (!p) return; means the allocation failed and nothing leaks. It tracks how big each buffer is and what range an index can take.

For Java it follows values from where they arrive (readLine, getParameter, environment variables) to where they do damage: a SQL string, a shell command, a file path, an HTML response.

Dead branchesA condition that is a constant, like if (DEBUG) with DEBUG set to 0, is folded away, so code that can never run doesn’t raise alarms.
3

It grades each finding by what it proves.

A copy proven to be larger than its destination is Critical. An unbounded strcpy whose source is a function parameter is High. The same strcpy of a short constant into a big enough buffer isn’t flagged at all.

Complexity and deep nesting are reported, but they never move the verdict. A long function is a maintenance problem, not a vulnerability.

Why not more red“High risk” needs a Critical or High security finding behind it. Style and reliability issues top out at Moderate.
4

Then four models weigh in.

Each model looks at the counts and shape of the findings and estimates a risk level. Their say is bounded by the evidence: no model can call code High risk without a serious finding behind it, and a serious finding always makes the verdict High, whatever the models say. Nor can a model call code Moderate when there is nothing concrete to point at.

That rule was chosen by measurement. Of three ways of combining the models with the findings, the one used here scored best on code the models had never seen.

What it gets wrong

A tool that only lists its strengths is selling something. These are the known gaps.

What it misses

  • Logic errors and wrong answers. It reads for memory and injection bugs, not for what your code was meant to do.
  • Integer overflow and signedness bugs.
  • Race conditions and time-of-check/time-of-use gaps.
  • Ownership that crosses functions or files: a pointer freed by a callee it can’t see.
  • In Java, data that crosses from one method into another before it reaches a query.
  • In C++, anything beyond new/delete pairing and the unsafe C calls.

What it over-calls

  • Long files. Small findings add up, so a file with dozens of functions is more likely to collect at least one Medium finding and be called Moderate.
  • An unchecked malloc is a real weakness but a low-stakes one; it lands on Moderate at most.
  • Java parameters of non-private methods are treated as possibly hostile, which is cautious by design.
  • Modern AES defaults such as Cipher.getInstance("AES") are flagged because the JDK default is ECB mode.
